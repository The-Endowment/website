# V1 reported reward collector

This implementation is prepared for review, with collection and new enrollment held closed by `COLLECTION_RELEASED = false`. No scheduler, live signing key, deployment, or pilot has been configured. The old HTTP sweep endpoint remains inert: the replacement needs a durable worker, not an ephemeral webhook invocation. The release gate is intentionally a reviewed source change, not an environment switch.

The policy is all verified StonkFun rewards paid in PUMP after fresh enrollment and an active observation boundary. Rewards from other StonkFun coins also qualify. Existing balances, purchases, ordinary transfers, STONK rewards and rewards already paid while waiting or paused never add eligibility. Outgoing PUMP consumes eligible rewards first; buying replacements cannot restore it. There is **no per-wallet daily cap**, as explicitly requested by the owner. Actual token allowance and the existing treasury inventory limit still apply. Inventory is limited to three days of what the buyback limits can spend; that is a treasury safeguard, not a daily contribution allowance per wallet.

## Trust and limitations

The contract verifies the reporter signature, owner consent, exact amount, next nonce, short expiry, lifecycle generations, source balance, delegation and fixed treasury destination. It does not prove that the reporter's classification is correct. A compromised reporter can authorize an incorrect collection, and there is no per-wallet daily loss limit. An observed balance equality does not prevent spending and buying the same amount after observation but before execution. The service additionally checks the finalized transaction cursor immediately before signing, narrowing that race without eliminating it. Broad SPL approval remains revocable directly with the token program. Retained program upgrade authority is a separate power to replace these rules.

The service requires both an API distribution record and a successful finalized transaction from the pinned distributor authority and source account. Batch token totals must agree. It uses actual net recipient credit, not an API estimate or a proportion of aggregate rewards. Nonmatching/missing API records leave rewards with holders. The public API feed is bounded at 100 records, so a slow worker or delayed API publication can miss rewards. A new distributor, source, or unsupported transfer format requires review before recognition; a sender address alone is insufficient.

Unknown token operations, mixed inflows/outflows, duplicate or ambiguous same-slot source transactions, account identity changes and incomplete history discard uncertain eligibility. This is deliberately conservative and can undercollect. The pledge describes what holders authorize, not a guarantee that every payout will be collected. No value or governance privileges should depend on successful collection ordering. Wallet iteration rotates its starting position daily, but treasury capacity and service timing can still affect participation fairness.

## Worker and durable state

Run `npm run reporter:once` with reviewed flagship constants/settings, `SOLANA_RPC_URL` and a durable `REPORTER_DATA_DIR`. The default is observation only: it writes audit records and hypothetical collection amounts without loading a key or broadcasting. The placeholder flagship creator currently prevents even an accidental mainnet instance selection.

After an independently reviewed and explicitly authorized release, `npm run reporter:once -- --submit` additionally requires `REPORTER_KEYPAIR_FILE`, a private 64-byte JSON Solana keypair file. The signer must match the on-chain reporter policy. Keep it separate from the refresher, treasury governance and program upgrade authorities. The HTTP keeper continues handling counts, refreshes and buys; it cannot replace the persistent reporter worker. Provisioning a supervised runner and choosing its interval/RPC capacity are deployment tasks. Nothing in this PR schedules a run.

Each PUMP account has an append-only hash-linked JSONL journal and an exclusive directory lock. Entries contain the current eligible balance, finalized cursor/slot, consent and lifecycle binding, classification evidence, and any prepared transaction. Amounts use integer base-unit strings. File and directory writes are synced before broadcast. The exact signed bytes, signature, nonce and blockhash lifetime are persisted before sending. A timeout leaves this outbox intact; no new authorization may bypass an unresolved submission.

Known finalized outcomes are reconciled against complete source history so an actual collection debit is counted once and remaining verified rewards are retained. Unknown expired transactions, lifecycle changes or history gaps establish a fresh zero-eligibility boundary. A successful funding-goal no-op is not a contribution. Never infer repayment or reward debt from the wallet's present balance.

A corrupted/truncated journal or a stale lock stops processing that account. Do not delete the journal and continue signing. Stop the worker, preserve the journal, reconcile any pending signature and on-chain nonce, then restore validated durable state or explicitly establish a new zero-eligibility boundary. A filesystem rollback, operator compromise, RPC misinformation or loss of state is outside the journal's integrity guarantee. A reviewed database/checkpoint/rotation approach is needed before logs grow beyond practical memory limits; this first implementation reads each account's log on open.

## Consent, deployment and versioning

Version 4 keeps Config/Landlord allocations unchanged by consuming reserved bytes, but requires newly initialized version 4 configurations and fresh holder consent. It does not silently migrate version 3 deployments or registrations. Existing approvals are not new consent. The UI checks the pinned flagship, policy and lifecycle, explains the trusted service and unlimited SPL allowance, and requires an unchecked consent box before approval plus enrollment/renewal. The release hold keeps this action unavailable today. Revoke/leave remains independent of the reporter and release gate.

Every new commitment count, pause, parameter application, refresher invalidation, consent renewal and reporter rotation invalidates old reporting evidence. Pending uncertain receipts at a boundary are left with the holder. Completion is permanent when the direct authenticated PENIS vault reaches 200M; LP holdings and historical purchases do not count. Reporter replacement has a 72-hour timelock, a one-day admin grace period and seven-day proposal expiry. Admin or the current reporter can disable collection immediately; the guardian retains only its existing bounded pause. Repeated disable cannot veto recovery. Renouncing admin permanently freezes reporter replacement and lost-key recovery, while a reporter can still disable itself.

The source review and automated tests are not an independent security audit. Production prerequisites remain verified treasury reward eligibility, an explicit upgrade-authority policy, deployment identity/toolchain validation, funded operator accounts and an authorized limited pilot. No production action is authorized by merging these local changes.

## Validation and operational checks

`npm test` covers receipt matching, net credits, spending/rebuying, inactive boundaries, duplicate and missing history, report encoding against the generated Anchor IDL, journal persistence/restart, and transaction reconciliation. Run lint, typecheck and production build alongside the paired contract's full SBF test suite. The saved IDL fixture must be refreshed with reviewed contract interface changes.

The existing `npm run sanity:daily` compares observed end-of-day holder collections with an approximate expectation from PENIS's public aggregate rewards and sampled commitment. Other PUMP-generating coins, minimum payout eligibility, changing holdings, capacity and timing affect this comparison. It is an investigation signal, never an authorization to debit wallets or proof of correct individual collection. Keep per-wallet journal review separate from the approximate daily aggregate check.
